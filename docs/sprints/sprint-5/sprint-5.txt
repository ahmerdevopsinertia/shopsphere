Before Writing the Schema

One more design decision.

Order Status

I recommend we define it now rather than adding values later.

enum OrderStatus {
  PENDING
  CONFIRMED
  PAID
  SHIPPED
  DELIVERED
  CANCELLED
}

Even though we'll initially use only PENDING, having the complete lifecycle from the start keeps the schema stable and avoids future enum migrations.

Why onDelete: Restrict?

Orders are business records.

If a user somehow becomes inactive or is removed from the system, their historical orders should remain. Restricting deletion prevents accidental loss of order history.

===

Why totalAmount on Order?

Even though we can calculate the total from the items, we store it because:

Faster queries
Simpler reporting
Stable order totals even if products change later

Example:

2 × 39 = 78
1 × 19 = 19

Total = 97

We save:

totalAmount = 97

rather than recalculating every time.


====


Important architectural decision:

Creating an order will involve:

Check products exist
Check inventory availability
Calculate total
Create Order
Create OrderItems
Reserve inventory

These are multiple database operations.

Therefore, unlike previous sprints, we cannot simply do:

await createOrder()

await updateInventory()

because this can happen:

Order created ✅

Inventory update fails ❌

Now we have corrupted data.

So the final implementation will use:

prisma.$transaction()

Example:

await prisma.$transaction(async(tx)=>{

    create order

    create order items

    reserve inventory

});

Either everything succeeds:

Order ✅
Items ✅
Inventory Reserved ✅

or everything rolls back:

Order ❌
Items ❌
Inventory ❌

Today your workflow is:

Imagine this happens:

Create Order Items      ✅

Step 1 — Extend OrdersRepository

Instead of exposing only:

create()

we'll expose one method responsible for the entire write operation.

Example:

async createOrder(
    userId: string,
    validatedItems: ...,
    totalAmount: number,
)

This method—not the service—will contain prisma.$transaction().

Why?

Because the Repository owns database operations.

The Service owns business rules.

This separation is consistent with the architecture we've followed since Sprint 1.

Step 2 — Transaction Structure

Inside OrdersRepository:

return this.prisma.$transaction(async (tx) => {

});

Notice:

tx

is a transactional Prisma client.

From this point onward:

❌ Don't use

this.prisma.order.create(...)

Use

tx.order.create(...)

Everything inside the callback participates in the same transaction.

Step 3 — Create Order
const order = await tx.order.create({
    data: {
        userId,
        totalAmount,
    },
});

status is omitted because Prisma applies the default:

PENDING
Step 4 — Create Order Items

Loop:

for (const item of validatedItems) {

}

Inside:

await tx.orderItem.create({
    data: {

        orderId: order.id,

        productId: item.product.id,

        quantity: item.quantity,

        unitPrice: item.unitPrice,

    },
});

Notice we're using the validated product, not the request DTO.

Step 5 — Reserve Inventory

Still inside the loop:

await tx.inventory.update({

    where: {

        productId: item.product.id,

    },

    data: {

        reserved: {

            increment: item.quantity,

        },

    },

});

This is exactly why we designed Sprint 4 with:

reserved

instead of immediately deducting quantity.

Step 6 — Return Order

After the loop:

return order;

If any statement throws an exception:

↓

↓

Nothing saved

🚀 Enterprise Improvement

There's one enhancement I'd make while we're implementing this.

Currently, your validation happens outside the transaction. That's good for performance because transactions stay short.

However, there's a small race condition:

User A validates that 5 units are available.
User B places an order and reserves those 5 units.
User A's transaction starts and reserves another 5 units.

This is a classic concurrency problem.

For our learning project, the current approach is perfectly acceptable and teaches the right concepts. In a production system with high traffic, we'd address this with stronger transactional guarantees (such as rechecking availability inside the transaction or using appropriate database locking/isolation strategies).

I suggest we keep the current design for Sprint 5 because it's clean, readable, and introduces transactions without adding advanced concurrency complexity. Later, once the full order workflow is complete, we can revisit this and evolve it into a production-grade reservation strategy.

🚀 Sprint 5 — Session 7
Order Status Management

Creating an order is only the beginning.

A real order changes state over time.

PENDING
    │
    ▼
CONFIRMED
    │
    ▼
PAID
    │
    ▼
SHIPPED
    │
    ▼
DELIVERED

Or

PENDING
    │
    ▼
CANCELLED
Business Rule

Not every transition should be allowed.

Example:

PENDING
   │
   ├──► CONFIRMED
   │
   └──► CANCELLED

After confirmation:

CONFIRMED
      │
      ▼
PAID

After payment:

PAID
     │
     ▼
SHIPPED

After shipping:

SHIPPED
      │
      ▼
DELIVERED

Notice:

DELIVERED

↓

PENDING ❌

should never happen.

Inventory Behavior

This is why we introduced reserved stock.

PENDING
Quantity = 100

Reserved = 2

Available = 98

Nothing leaves the warehouse yet.

PAID (or SHIPPED)

Now the warehouse packs the item.

Inventory becomes:

Quantity = 98

Reserved = 0

Available = 98

Notice:

Quantity--

Reserved--
CANCELLED

Customer cancels before shipping.

Quantity = 100

Reserved = 0

Available = 100

Only:

Reserved--

Quantity stays the same.

This is exactly why we designed Sprint 4 the way we did.

+

Use the enum directly.

Repository

We'll add:

findByIdForUpdate(id: string)

Notice the difference.

Current API:

Admin APIs shouldn't.

We'll therefore create a separate repository method.

Service Flow
Find Order

↓

Validate Transition

↓

Transaction

    Update Order

    Update Inventory

↓

Return Response
Allowed Transitions

We'll explicitly enforce:

Current	Next	Allowed
PENDING	CONFIRMED	✅
PENDING	CANCELLED	✅
CONFIRMED	PAID	✅
PAID	SHIPPED	✅
SHIPPED	DELIVERED	✅

Everything else:

400 Invalid status transition.

This keeps the workflow deterministic and prevents accidental regressions.

Inventory Updates

Inside the transaction:

CANCELLED
reserved -= ordered quantity
PAID
quantity -= ordered quantity

reserved -= ordered quantity

Later, if your business decides to deduct inventory at SHIPPED instead of PAID, you only need to change this one rule.

Repository Method

We'll add a dedicated repository method similar to createOrder(), for example:

updateStatus(
  orderId,
  status,
)

This method will:

Start a transaction.
Update the order status.
Update inventory for every order item (depending on the new status).
Commit or roll back.

Again, the repository owns the database transaction, while the service owns the business rules.
