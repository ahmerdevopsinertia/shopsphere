Step 3 — Add Lint

Before changing anything, check your backend/package.json for:

"scripts": {
  "lint": "...",
  "test": "...",
  "build": "..."
}

If lint already exists, add this immediately after npm ci:

- name: Run lint
  run: npm run lint

So the current workflow becomes:

name: ShopSphere CI

on:
  push:
    branches:
      - main
      - develop

  pull_request:
    branches:
      - main
      - develop

  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest

    defaults:
      run:
        working-directory: backend

    steps:
      - name: Checkout repository
        uses: actions/checkout@v6

      - name: Setup Node.js
        uses: actions/setup-node@v7
        with:
          node-version: '22'
          cache: npm
          cache-dependency-path: backend/package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Run lint
        run: npm run lint

      - name: Build application
        run: npm run build

The current GitHub documentation recommends setup-node for selecting Node versions and supports npm dependency caching through the action.

Why I'm changing @v4 → @v6/@v7

Your screenshot's warning is related to the runtime used internally by the Actions themselves, not Node 22 that your application uses.

Current GitHub documentation examples use:

actions/checkout@v6
actions/setup-node@v7

So let's use the current versions rather than carrying the warning into the production pipeline.

Step 4 — Tests

After lint passes, we'll add:

- name: Run tests
  run: npm test

But don't add this yet if your project doesn't currently have a reliable test suite.

Given ShopSphere's current stage, I'd actually prefer:

Lint
 ↓
Unit Tests
 ↓
Build

rather than blindly running tests and potentially discovering that Jest/configuration isn't CI-ready.

Step 5 — Docker build

Once:

npm ci       ✅
lint         ✅
tests        ✅
build        ✅

we'll add Docker.

Since your Docker configuration is already working locally, we'll build the image in GitHub Actions.

Something along the lines of:

- name: Build Docker image
  run: docker build -t shopsphere-backend:ci .

The exact context depends on where your Dockerfile currently lives.

Don't push the image anywhere yet.

First we'll prove:

GitHub runner can successfully build the same Docker image that works on your Mac.

Step 6 — Run the Docker container

Then we'll go one step further:

Docker Build
     ↓
Docker Run
     ↓
Health Check
     ↓
Stop Container

This is particularly important for ShopSphere because your application has:

PostgreSQL
Prisma
JWT configuration
environment validation
seed configuration
Docker networking

We shouldn't consider CI/CD complete just because docker build succeeds.

Step 7 — Docker Registry

After the above works, we'll decide where to publish the image.

For your project, I recommend GitHub Container Registry (GHCR) because your source code is already on GitHub.

Architecture:

GitHub
   │
   ├── CI
   │    ├── npm ci
   │    ├── lint
   │    ├── tests
   │    └── build
   │
   └── CD
        │
        ├── Docker build
        │
        ├── Docker image
        │
        └── GHCR
              │
              ▼
       shopsphere-backend

GitHub officially supports publishing Docker images to ghcr.io using GITHUB_TOKEN, so we don't need to introduce Docker Hub credentials unnecessarily.
